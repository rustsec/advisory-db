# Crafted HTTP redirects can bypass the credential-reuse guard

The HTTP redirect guard in `gix-transport` compares URL authorities using `gix-url`. A parser regression fails to terminate an authority at `?` or `#`, so a redirect such as `https://attacker.example?@trusted.example/repo` can appear to have the trusted host while the HTTP client connects to the attacker.

With the curl HTTP backend, an attacker who controls a redirect response from an origin the caller authenticates to can make the guard retain that origin's HTTP Basic credentials. Curl removes authorization when following a cross-host redirect, but `gix-transport` can attach the retained credentials to the subsequent POST. Exposure requires an authenticated HTTP workflow that follows the crafted redirect. Initial redirects are enabled by default. The cleartext HTTP reproducer additionally requires `http-client-insecure-credentials`; an HTTPS workflow does not require that feature.

The affected authority guard first shipped in `gix-transport` 0.56.0. Earlier releases' unguarded credential forwarding is a separate issue covered by [GHSA-9857-6mw7-fq2m](https://github.com/advisories/GHSA-9857-6mw7-fq2m). The `unaffected` range below 0.56.0 applies only to this guard bypass.

Update to `gix-transport` 0.58.1 or later, which requires the fixed `gix-url` 0.37.1 parser. A compatible dependency update can also remediate an affected transport release when its dependency range admits `gix-url` 0.37.1. Disabling HTTP redirects avoids the reported credential-disclosure path.

Reported by GitHub user `shuvamk`, with AI assistance disclosed in the original report.
