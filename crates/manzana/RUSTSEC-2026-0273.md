# Stubbed cryptography without warnings

The `manzana` crate appears to be a work-in-progress module for the Apple Silicon chips' features, including the Secure Enclave.

This crate's description and `README`s make no hint at the fact that the [`SecureEnclaveSigner`](https://docs.rs/manzana/0.2.0/manzana/secure_enclave/struct.SecureEnclaveSigner.html) type is a stubbed implementation that does not actually perform any cryptographic operations, and instead returns fixed values.

Unsuspecting users of the crate, who may not check the source code, receive no warning about this and may believe they are using a secure implementation when they are not.

There are currently (as of `2026-04-07`) no versions of the crate that contain either a real implementation, or a warning about the stubbed cryptography.

## Resolution

Fixed in 0.3.0 by **removing the cryptography entirely** rather than implementing it.

`secure_enclave` and the Security-framework FFI are deleted. manzana 0.3.0
performs no cryptographic operation, makes no Security framework call, exports
no key, signature, or signer type, and declares no cryptography dependency. For
Secure Enclave and Keychain access, use the
[`security-framework`](https://crates.io/crates/security-framework) crate.

0.1.0 and 0.2.0 remain yanked.

The same fabricate-a-plausible-value pattern existed outside the module this
advisory names, and was removed in the same release: `neural_engine::infer()`
returned `Tensor::zeros(input.shape)`; `neural_engine::capabilities()` returned
the M1's published figures on every chip; `neural_engine::load()` reported a
loaded model after checking only the filename; `metal::dispatch()` returned
`Ok(())` having dispatched nothing; `metal::compile_shader()` "compiled" by
hashing the source string; and a missing IOKit registry key defaulted to
Apple's marketed Afterburner stream capacity. In 0.3.0 every operation that
cannot reach hardware returns `Err(Error::Unimplemented)`.

## Note on the affected platform

The `arch = ["aarch64"]` constraint has been dropped from `[affected]`, because
the affected code was not aarch64-specific and the narrower constraint
under-reported who was exposed.

`SecureEnclaveSigner::is_available()` was `#[cfg(target_os = "macos")] true` —
a compile-time constant with no runtime probe — so it returned `true` on x86_64
macOS hosts with no Secure Enclave at all, and `sign()`/`verify()` then
"succeeded" there exactly as they did on Apple Silicon. Intel Mac users were
equally affected and, with `arch = ["aarch64"]` set, were not warned by
`cargo audit`.
