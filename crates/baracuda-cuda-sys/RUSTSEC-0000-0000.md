# FFI struct mirrors smaller than the CUDA ABI: out-of-bounds write and read through safe wrappers

Several `#[repr(C)]` mirrors of CUDA structs in `baracuda-cuda-sys` were smaller than the C structs of the same name in the CUDA headers, so the CUDA libraries read or wrote past the Rust object:

- `cudaPointerAttributes`: the Rust mirror was 24 bytes; the C struct ends in `long reserved[8]` and is 56 bytes on Windows (88 on LP64 Linux). `cudaPointerGetAttributes` writes the whole C struct. The safe function `baracuda_runtime::query::pointer_attributes` passed a stack `cudaPointerAttributes` to it, so every call overran the stack object by 32 bytes (64 on LP64 Linux).
- `cudaResourceViewDesc`: the Rust mirror was 48 bytes; the C struct is 112 (it ends in `unsigned int reserved[16]`, "must be zero"). The safe `baracuda_runtime::array::TextureObject::new` takes `Option<&cudaResourceViewDesc>` and hands it to `cudaCreateTextureObject`, which is entitled to read 64 bytes beyond the Rust object.
- `CUdevSmResource` lacked the `flags` field (12 bytes instead of 16) and `CUlaunchAttributeValue` / `CUlaunchAttribute` were 1-aligned instead of 8-aligned. These are layout mismatches; no out-of-bounds access through a safe function was identified for them.

The struct definitions are identical in every published version from 0.0.1-alpha.1 through 0.0.1-alpha.126 (compared in the published crate files).

Fixed in 0.0.1-alpha.137 (the lockstep release family; alpha.127 to alpha.136 were never published): the mirrors have the C sizes and alignments, and a new `layout.rs` asserts the size and alignment of 60 structs at compile time against values taken from the CUDA 13.3 headers.

Impact: memory corruption (stack overwrite with driver-written data) or an out-of-bounds read of adjacent memory from safe Rust code, by calling `baracuda_runtime::query::pointer_attributes` or passing a view descriptor to `TextureObject::new`. Crates that depend on `baracuda-cuda-sys` (`baracuda-runtime`, `baracuda-driver`) are affected through it until they and this crate are upgraded together. Whether the overrun occurs depends on the installed CUDA runtime; the 32-byte write was observed with a CUDA 13.x runtime. Action: upgrade to 0.0.1-alpha.137 or later (and the other `baracuda-*` crates to the same release). No workaround other than not calling the affected wrappers.
