# Unbounded memory allocation in `cpio` parsing a newc archive header

Affected versions of `cpio` did not bound the entry-name length read from a newc (SVR4) cpio header before allocating a buffer sized from it, allowing a tiny crafted archive to force a multi-gigabyte allocation and abort the process (out-of-memory denial of service, CWE-400).

## Details

In `Reader::new` (`src/newc.rs`, reached through the public `cpio::NewcReader::new`), the entry name length `c_namesize` is read as an 8-char ASCII-hex `u32` straight from the header and used to size a zeroing buffer before any name bytes are read:

```rust
let name_len = read_hex_u32(&mut inner)? as usize;   // c_namesize, straight from the header
// ...
let mut name_bytes = vec![0u8; name_len];            // unbounded allocation, sized from the file
inner.read_exact(&mut name_bytes)?;                   // only fails AFTER the allocation
```

There is no check that `name_len` fits within the bytes remaining in the input, so a header declaring a ~4 GiB name length makes the crate request a ~4 GiB allocation from an archive of only ~110 bytes. So reading a cpio-archive with `cpio::NewcReader::new` on attacker-controlled input exhausts memory and can OOM-kill the process.

## The fix

`0.4.2` grows the name buffer as bytes arrive instead of pre-sizing it from the untrusted length, and rejects truncated names.
