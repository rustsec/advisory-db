# `Clone` for `Value` and `Atom` can wrap QuickJS-NG's reference count

`Clone` for `Value` calls `JS_DupValue`, and `Clone` for `Atom` calls `JS_DupAtom`. QuickJS-NG keeps these reference counts in an `int` and increments them with no upper bound. `std::mem::forget` is safe, so safe code can clone a value or atom and forget the clones until the count passes `INT_MAX`, which is a signed overflow and undefined behavior in C. In our builds the count then wrapped around to a small value, and dropping one handle freed the object while another handle still pointed to it.

Separate `#![forbid(unsafe_code)]` drivers trigger this with rquickjs-core 0.14.0 and rquickjs-sys 0.14.0, which bundles QuickJS-NG 0.16.2. For `Value`, the driver keeps two handles to one object, forgets 2^32 - 1 clones, and drops one handle; a property read through the other handle then crashes with SIGSEGV. For `Atom`, after the same number of forgotten clones and one drop, the surviving handle reads a different atom that took the freed slot, and the process then crashes with SIGSEGV during teardown. With no forgotten clones, the surviving `Value` returned the expected property and the surviving `Atom` returned the original string.

The rquickjs issues were closed with a pointer to QuickJS-NG, and QuickJS-NG declined to bound the count. No fixed version is available.
