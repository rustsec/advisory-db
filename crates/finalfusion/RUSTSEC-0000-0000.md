# Unbounded allocations when reading embedding files from untrusted sources

All binary-format readers in `finalfusion` allocate buffers directly from
lengths, counts and shapes declared in the (untrusted) input file, before any
format validation takes place. A small malicious file can trigger a huge
single allocation, or an allocation-failure abort, in any process that parses
embedding files from untrusted sources (user uploads, downloaded models).

Measured on 0.18.0 with a counting global allocator:

- 20-byte file: header + `Metadata` chunk declaring `chunk_len = 1 GiB` →
  single allocation of 1,073,741,824 bytes before reading any TOML byte.
- 70-byte file: `NdArray` chunk declaring `rows = 1, cols = 268,435,456` →
  single allocation of 1,073,741,824 bytes.

11 allocation sites are affected, including `Metadata::read_chunk`, `NdArray`,
`NdNorms`, `QuantizedArray`, the shared `read_string` / `read_vocab_items`
helpers, and the word2vec / fastText / floret readers.

No patched version exists. A fix that grows every buffer from the bytes
actually read, with regression tests, is available in
[PR #203](https://github.com/finalfusion/finalfusion-rust/pull/203).

The crate is unmaintained: the repository has had no commits since October
2023, the last release was 0.18.0 in October 2023, and the maintainer has not
responded to any issue since August 2024. The vulnerability was publicly
disclosed in [issue #204](https://github.com/finalfusion/finalfusion-rust/issues/204)
with no response.
