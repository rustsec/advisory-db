# `MappedLine` can outlive the GPU context that owns its memory

In versions before 0.1.1, `backend::cuda::MappedLine::new` (feature `cuda`) and
`backend::hip::MappedLine::new` (feature `hip`) allocate a pinned, device-mapped host page in
the calling thread's current context, but do not take a reference to that context. If safe
code destroys or releases the context before dropping the line, the driver frees the page
with the context. Two things then happen:

- `MappedLine::line()` returns a reference into unmapped memory. Reading it through the safe API
  faults (SIGSEGV, reproduced on an NVIDIA GB10, driver 580, CUDA 13.0).
- A line made later in a new context can be handed the same address. A store through the stale
  line is then read through the new line, and dropping the stale line frees the new line's page.

Safe context owners can trigger this, for example `cudarc::driver::CudaContext`. Its `Drop`
releases the primary context, or destroys a non-primary one.

The 0.1.0 README stated that this use-after-free was "excluded by construction". That statement
was incorrect.

## Fix

From 0.1.1, a line belongs to the primary context of the current context's device and holds its
own reference to it (`cuDevicePrimaryCtxRetain` / `hipDevicePrimaryCtxRetain`) until after the
page is freed. Stores from streams of non-primary contexts are refused with
`LineError::ForeignStream`. The remaining assumption is that nothing resets the device while a
line is alive (`cuDevicePrimaryCtxReset`, `cudaDeviceReset`, `hipDeviceReset`). A reset
invalidates every allocation in the process regardless of references.

## Workaround for 0.1.0

Keep the context alive (and current-device ownership unchanged) until every `MappedLine` made in
it has been dropped.
