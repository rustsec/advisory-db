 Missing public input length check in Groth16 verifier

 Groth16::prepare_inputs does not check that public_inputs.len() + 1 equals pvk.vk.gamma_abc_g1.len(). It indexes gamma_abc_g1[0] and then folds public_inputs with gamma_abc_g1[1..] through Iterator::zip, returning Ok either way (src/verifier.rs in 0.6.0). Groth16::verify_proof and
 SNARK::verify_with_processed_vk do not check the length before calling it.

 ark-groth16 0.4.0 and 0.5.0 rejected this case with SynthesisError::MalformedVerifyingKey. That variant was removed from ark-relations 0.6.0, and 0.6.0 dropped the check instead of returning another error. The same code is on master at 8f0904a7d7a2c8945bf770bdd3c2081e0be1941a, so every
 version since 0.6.0 is affected. No release fixes it.

 If the slice is longer than the verifying key, zip stops at the key and the trailing inputs never enter the pairing equation. A proof for (x_0, ..., x_{k-1}) then verifies as Ok(true) for (x_0, ..., x_{k-1}, y_k, ..., y_{m-1}), whatever the trailing values are. If the slice is shorter, the
 missing terms are left out of the sum, which is the same as verifying against those inputs set to zero. An empty gamma_abc_g1, as produced by VerifyingKey::default(), panics on the [0] index instead of returning an error.
 The in-circuit verifier (Groth16VerifierGadget::verify_with_processed_vk, src/constraints.rs, r1cs feature) has its own check for the same length, and that check is also wrong: assert!(input_len == gamma_abc_g1.len() && public_inputs.next().is_none()) runs after by_ref().zip(...). zip
 consumes one extra element from the left iterator once the right iterator ends, so a slice that is exactly one input too long passes the assertion. That is the same missing invariant, not a second bug.

 A caller that already compares the slice length to the verifying key is not affected, and a proof still only attests to the statement it was created for.
