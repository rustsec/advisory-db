# `RawVec::resize` calls `realloc` on a dangling pointer when growing from zero capacity

`RawVec::try_resize` calls `realloc` on its pointer whenever the new layout is
non-zero. If the current capacity is 0 (`RawVec::new()` or
`RawVec::with_capacity(0)`), the pointer is `NonNull::dangling()` and was never
allocated, so `realloc` is passed a pointer that the global allocator does not
own. This is undefined behavior reachable from safe code:

```rust
let mut v = owned_alloc::RawVec::<u64>::new();
v.resize(4);
```

On `x86_64-pc-windows-msvc` this aborts the process with
`STATUS_HEAP_CORRUPTION`, and Miri reports the dangling pointer passed to
`realloc`. `RawVec::resize` delegates to `try_resize`, so both are affected.

## Fix

No fixed release is available. The crate has had no release since 2018 and the
maintainer has not responded to earlier reports. Users can avoid the bug by
never resizing a `RawVec` whose capacity is 0, or migrate to
`Vec::with_capacity` / `Vec::try_reserve` from the standard library.
