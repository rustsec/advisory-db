# Server secret-manager secrets readable through vars: substitution in faucet serve

**Summary.** A principal allowed to submit pipeline configs (the `operator` role, or any principal of a `--no-auth` server) could assemble a secret-manager reference (`${vault:…}`, `${aws-sm:…}`, `${gcp-sm:…}`, `${azure-kv:…}`) from fragments substituted through `${vars.*}`, `${sources.*}` or `${sinks.*}`. The server resolved it with its own secret-manager credentials, even though the same reference written directly was refused unless `--allow-secret-scheme` allowed it. The submitter could then route the value somewhere they control, for example as a header on a REST source.

**Fix.** Substituted text can no longer form a `${…}` directive, and every secret-manager reference is checked against the caller's reference policy immediately before it is fetched.

**Workaround.** Don't give the `faucet serve` process secret-manager credentials (`VAULT_TOKEN`, cloud credentials) beyond what its operator-written configs need, and restrict which principals hold the `operator` role.

**Affected:** `faucet-cli` <= 1.16.0, including the prebuilt binaries and container images of those versions. **Patched:** 1.17.0.

This applies only to `faucet serve`: configs submitted to a running server through the HTTP API, MCP, triggers or templates. One-shot `faucet run` and `faucet schedule` runs of the operator's own configs are not affected.
