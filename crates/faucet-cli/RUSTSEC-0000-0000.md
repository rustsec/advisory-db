# faucet serve runs a caller's inline deployment overlay with server trust

**Applies only to `faucet serve` with the template registry** (the `templates` feature, included in the prebuilt binaries and the `full` container image). One-shot `faucet run` / `faucet schedule` are not affected.

### Summary
When a template run is triggered, the caller may pass a deployment overlay: operational blocks such as `state`, `dlq`, `notifications`, `schedule` and `resilience`. A registered overlay is server-owned, but an *inline* overlay is written by the caller. Versions 1.13.0 through 1.15.0 merged an inline overlay into the template body and ran the result with the trust of a server-owned template. The checks the server applies to caller-submitted configs were skipped.

The affected entry points are `POST /v1/templates/{id}/runs`, the tenant template-run route, and the MCP `run_template` tool. Any principal allowed to trigger a template run could exploit it: the `operator` role, a tenant-scoped principal (which is otherwise refused raw configs), or any caller of a `--no-auth` server.

### Impact
Through the overlay, a caller could:
- **run a program on the server** with a subprocess DLQ sink (a Singer target), even when the server was not started with `--allow-subprocess-connectors`;
- **read and write arbitrary files** the server's user can access, through a file DLQ sink or a file state store;
- **read the server's environment variables, files and secret-manager entries** with `${env:}`, `${file:}` and `${secret:}` directives, which were resolved with the server's own environment, and send them out through a notification webhook;
- **make requests to internal hosts** through notification URLs or an HTTP DLQ sink.

### Fix
Fixed in 1.15.1. An inline overlay is treated as caller input: it is screened under the caller's reference policy (references, local paths, URLs, subprocess connectors) before it is merged, and tenant-scoped principals may not send one. Registered overlays are unchanged.

### Workaround
Upgrade to 1.15.1 or later. If you cannot upgrade, restrict which principals hold the `operator` role, don't give tenant-scoped principals access to the server, and don't run `--no-auth` on a reachable address.
