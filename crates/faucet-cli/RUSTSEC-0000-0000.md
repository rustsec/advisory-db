# Cross-site requests can drive a faucet serve --no-auth server on loopback

**Summary.** A `faucet serve --no-auth` instance on loopback (the local-development mode) had two gaps:
- it accepted `text/plain` cross-origin POSTs to `/mcp` and to webhook triggers, which need no CORS preflight;
- it accepted any `Host` header, so a DNS-rebinding page could reach every `/v1` route as the anonymous admin.

Combined with GHSA-h63h-q535-rjmj (path-root bypass) and GHSA-g9mq-7qqc-w5x4 (environment file readable as pipeline data), a malicious web page could read and write files on the developer's machine.

**Fix.**
- `/mcp` requires `application/json`.
- Webhook triggers accept only their configured `content_types` (JSON by default).
- A `--no-auth` loopback server answers only `localhost`, `127.0.0.1`, `[::1]` and its listen address.
- State-changing requests from another origin are refused.
- New `--allowed-host` / `--allowed-origin` flags.

**Workaround.** Don't run `--no-auth` while browsing untrusted sites; use `--auth-token` even locally.

**Affected:** `faucet-cli` <= 1.16.0, including the prebuilt binaries and container images of those versions. **Patched:** 1.17.0.

This applies only to `faucet serve`: configs submitted to a running server through the HTTP API, MCP, triggers or templates. One-shot `faucet run` and `faucet schedule` runs of the operator's own configs are not affected.
