# X25519 accepts low-order public keys, yielding session keys computable without a private key

Versions of dryoc before 1.0.0 never reject low-order peer public keys or an
all-zero shared secret. In addition, versions 0.5.1 through 0.9.x compute
X25519 with the clamped scalar reduced modulo the prime subgroup order ℓ
(`Scalar::from_bytes_mod_order(clamp(n))`) instead of the clamped integer
specified by RFC 7748; earlier versions use the unreduced clamped scalar.
libsodium, with which these functions are documented as compatible, returns an
error for all of these inputs.

This affects `crypto_scalarmult`, `crypto_kx_client_session_keys` /
`crypto_kx_server_session_keys`, `kx::Session::new_*`, and
`crypto_box_beforenm` together with the box and precalculation APIs built on
it, whenever the peer public key is not authenticated or can be chosen by a
malicious party.

## Impact

- **Predictable session keys.** For the 14 encodings of low-order Curve25519
  points, the X25519 output is always the all-zero value in versions up to
  0.5.0, and one of 5 fixed public values in 0.5.1 through 0.9.x. The
  key-exchange functions return `Ok`, and anyone who knows the two public keys
  can recompute the resulting session keys (or `crypto_box_beforenm` key) by
  trying at most 4 candidates. The confidentiality and integrity of that
  session are lost, including against passive observers.
- **Small private-key leak (0.5.1 through 0.9.x).** With a peer key that has an
  order-8 torsion component, the output reveals 2 bits of the victim's static
  X25519 scalar to the peer (and, when the peer key is an order-8 low-order
  point, to any observer who can test the candidate session keys). This does
  not meaningfully reduce the hardness of recovering the key.
- **Non-standard output (0.5.1 through 0.9.x).** Peer keys with a torsion
  component, and points on the quadratic twist, produce outputs that differ
  from RFC 7748 and libsodium, which breaks interoperability for such keys.
- `KeyPair::is_valid_public_key` accepts 6 of the 14 low-order encodings, so it
  cannot be relied on as a guard.

Applications that only use authenticated peer keys generated by dryoc or
libsodium are not affected in practice: honest keys lie in the prime-order
subgroup, where the reduced and unreduced scalars give the same result.

## Resolution

Upgrade to dryoc 1.0.0 or later. In 1.0.0, X25519 is computed with
`MontgomeryPoint::mul_clamped` (the unreduced clamped scalar, as in RFC 7748),
and an all-zero shared secret is rejected, so low-order public keys now return
an error from the scalarmult, box, key-exchange and precalculation APIs. Note
that 1.0.0 is a backward-incompatible release; several of these functions now
return `Result`.

If upgrading is not yet possible, validate every untrusted peer X25519 public
key before passing it to dryoc 0.9.x, for example by rejecting keys that do not
map to a torsion-free Edwards point (`MontgomeryPoint::to_edwards(0)` followed
by `is_torsion_free()` in `curve25519-dalek`; this requires `curve25519-dalek`
4.x as a direct dependency). A check based only on `is_small_order()` prevents
the predictable session keys but not the 2-bit leak or the non-standard output.
