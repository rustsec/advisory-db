# Ed25519 signing key pairs with an inconsistent embedded public key are accepted

An Ed25519 secret key in `dryoc` is 64 bytes: the 32-byte seed followed by
the 32-byte public key. When signing, the public key used in the challenge
hash `k = H(R || A || M)` is read from bytes 32..64 of the secret key, while
the nonce `r`, and therefore `R`, is derived only from the seed and the
message.

In affected versions, `SigningKeyPair::from_slices` and, when the `serde`
feature is enabled, the derived `Deserialize` implementation of
`SigningKeyPair` store the 64 secret-key bytes as given, without checking
that the embedded public key matches the one derived from the seed. The
separate `public_key` field of the struct is not used for signing, so only
the embedded half is relevant. `SigningKeyPair::from_secret_key` re-derives
the key pair from the seed and is not affected.

If an attacker can replace bytes 32..64 of a stored secret key without being
able to read the seed, and can obtain signatures over the same message from
both the original and the modified key, the two signatures share the same `R`
and differ in `S`. The private scalar can then be computed as
`a = (S1 - S2) / (k1 - k2)`, which allows signatures to be forged for
arbitrary messages under the original public key. Examples of such conditions
are key storage without integrity protection, or an application that
assembles the 64 secret-key bytes from two separate sources. The upstream
advisory rates the issue as low severity.

This behavior matches libsodium, which also trusts the embedded public key,
so it is not a compatibility defect; the concern is that the higher-level
constructors in `dryoc` did not enforce the consistency that
`from_secret_key` already provides.

## Fix

Version 2.0.1 validates imported Ed25519 key pairs in
`SigningKeyPair::from_slices` and during serde deserialization, rejecting key
material whose embedded or separate public key does not match the seed. In
addition, `SigningKeyPair` signing and `Ed25519phSigner` finalization
re-derive the embedded public key from the seed, since the key pair's fields
remain publicly mutable.

The Classic API (`dryoc::classic::crypto_sign`) keeps libsodium-compatible
semantics: callers of functions such as `crypto_sign_detached` must supply
consistent signing key material.

Users should upgrade to `dryoc` 2.0.1 or later.
