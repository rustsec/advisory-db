# Base OT auxiliary point has a known discrete logarithm, leaking key shares

The base oblivious transfer (endemic OT of Zhou et al., eprint 2022/1525),
used to set up the OT extension for the multiplication subprotocol, derived its
auxiliary point as `h = hash_to_scalar(session_id, seed) * G`. The `seed` is
chosen by the OT receiver and sent to the OT sender, so the OT sender can
compute the discrete logarithm `eta` of `h`. Given the receiver's encryption
`(u, v) = (r*h, r*G + b*h)`, the sender recovers the choice bit `b` by checking
`eta * v == u`.

In the OT extension, the base-OT choice bits are the extension sender's
correlation. A party that learns it can unmask the extended OTs and recover the
counterparty's multiplication inputs (secret key share and nonce share).
Because every pair of parties runs the protocol in both directions, one
malicious participant in a single DKG (or complete refresh) and a subsequent
signing session can recover every other party's key share and reconstruct the
full signing key. The attacker only sends honest messages, so the attack is
undetectable.

The flaw was corrected in commit
[9f4061c](https://github.com/0xCarbon/DKLs23/commit/9f4061c578564d52e466a6ddfe39dbf14c2aaa0c)
by deriving `h` with RFC 9380 `hash_to_curve`. Upgrading does not repair
existing keys: their base-OT outputs are stored in the key shares. Run a
complete refresh on the fixed version if every party was trusted; otherwise
generate a new key and move assets. All parties must upgrade together.

Reported by Luca Dolfi.

`dkls23` is deprecated. Version 0.3.1 is a re-export of `dkls23-secp256k1`
0.5; make sure it resolves `dkls23-core` >= 0.5.2, or migrate to
`dkls23-secp256k1` / `dkls23-secp256r1` directly.
