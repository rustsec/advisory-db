# `Local` (`Rc`) backed strings and byte strings are `Send`, allowing data races

Affected versions of this crate implemented `Send` for `HipByt<B>` (and so for
`HipStr<B>`, `HipOsStr<B>` and `HipPath<B>`), and for the internal shared
pointer, whenever the backend `B` is `Send`. The thread-local backend `Local`
(the `Local*` type aliases) keeps its reference count in a `Cell<usize>`, which
is `Send` but not `Sync`: such a value could be sent to another thread while a
clone stayed behind, and cloning, dropping or checking uniqueness on both
threads then updates or reads the count without synchronization.

This is a data race (undefined behavior) reachable from safe code, for example:

```rust
let mut a = hipstr::LocalHipByt::with_capacity(62);
let b = a.clone();
std::thread::scope(|s| {
    s.spawn(move || {
        a.as_mut_ptr();
    });
    drop(b);
});
```

The default, thread-safe types (`HipStr`, `HipByt`, … with the `ThreadSafe`
backend) are not affected. Versions before 0.5.0 are not affected either: their
`Local` backend was std's `Rc`, which is not `Send`.

The flaw was corrected in 0.8.1 by requiring the backend to be `Sync` in these
`Send` implementations, so that `Local` values are no longer `Send`. The
affected versions (0.5.0 to 0.8.0) have been yanked; 0.5, 0.6 and 0.7 users
should upgrade to 0.8.1.
