# Server did not enforce authentication or authorization (dev-mode admin for any credential, unchecked tenant and variable operations)

The Commy WebSocket server (`src/server/ws_handler.rs`, entry point `server::ws_handler::handle_connection`) did not enforce authentication or authorization.

- Dev-mode authentication was always on. `Authenticate` ignored the supplied credential, defaulted the tenant, set the session tenant to the client's own string, and granted the administrator permission set plus every service permission. There was no configuration switch or `cfg` gate, on either the JSON path or the binary path. Present in 0.1.0 through 0.3.1.
- Tenant operations were unchecked. `CreateTenant` and `DeleteTenant` required no session or permission (and `DeleteTenant` removed nothing but replied success). Present in 0.1.0 through 0.3.1.
- Variable operations were unchecked. `ReadVariable`, `WriteVariable`, `AllocateVariable`, `DeallocateVariable` and `ReportVariableChanges` looked up a service by a client-supplied service id and never consulted session state, so an unauthenticated connection could read and write a service whose id it knew, including across tenants. Present in 0.2.0 through 0.3.1 (the 0.1.0 variable arms were not checked).

Affected: 0.1.0 to 0.3.1, every published version before the fix (all of them are yanked). Fixed in 0.4.1 (0.4.0 was never published): dev authentication is off by default and needs an explicit opt-in (`COMMY_ALLOW_DEV_AUTH` or `Server::with_dev_auth(true)`, logged loudly); one guard in the dispatcher refuses every operation from an unauthenticated session; `DeleteTenant` is truthful. Because no real credential verifier exists yet, with dev mode off nobody can authenticate: the server fails closed until real authentication is wired in.

Impact: anyone who can reach the server port gets administrator access (create and delete tenants, read and write service data). Workaround before upgrading: do not expose the server beyond localhost or a trusted network.
