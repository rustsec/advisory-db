# Uninitialized read and stale tokens in `PeekableLexer` lookahead

`PeekableLexer` buffers up to four lookahead tokens in an array of `MaybeUninit<Result<Token, LexError>>` guarded by two `u8` cursors. The loop that is supposed to lex forward to the requested offset iterates the inclusive range `write..=read`, which is empty whenever the requested offset is ahead of the number of buffered tokens. A forward peek therefore skips lexing and then calls `assume_init()` on a slot that was never written; because `Token` contains a fieldless enum, this materialises an uninitialized discriminant, which is undefined behavior (reproduced under Miri).

Independently of the undefined behavior, consumed ring slots are never cleared, so `peek1()` can return an already-consumed token instead of `None`.

The unsound path is reachable from safe code: `Parse` is a public, unsealed trait, so any downstream crate implementing it obtains a `&mut Parser` and may request an offset ahead of the buffered token count before parsing.

The vulnerable lexer was experimental and was deleted during the parser consolidation (commit `4d8f02d023`, included in `surrealdb` 4.0.0). The 4.0.0 parser is published as the separate `surrealdb-parser-next` package, so no release of `surrealdb-parser` itself contains the fix; the last release is 3.3.5.
