# A child launched with `Launch::spawn_in_job` can outlive its kill-on-close job

`Launch::spawn_in_job` created the child process suspended, assigned it to the
job object, and then resumed it. Between creation and assignment the child was
not a member of the job. If the parent process was terminated in that interval,
for example by `TerminateProcess`, a crash or a service stop timeout, none of
its destructors ran and the kill-on-close job did not cover the child. The
child stayed behind, suspended, together with the handles it had inherited.

The orphaned child never runs an instruction, and the interval is the time
between two system calls in the parent. The result is a leaked process and
leaked handles, for example a pipe end that never reports end-of-file to its
peer. It is not code execution, and it is not an escape from an AppContainer.

All versions before 0.1.4 are affected. Code that calls
`Launch::spawn_suspended` and then `Job::assign` itself has the same gap.

The flaw was corrected in 0.1.4, which creates the child inside the job with
`PROC_THREAD_ATTRIBUTE_JOB_LIST`, so the child never exists outside it. This
needs Windows 10 or Windows Server 2016.

As a workaround on affected versions, put the parent itself in a kill-on-close
job with `Job::assign_current_process` before it launches children. A child is
created in its parent's job, so it is covered from the start.

Thanks to YoshiiDev for reporting this issue.
