# Unbounded memory allocation in `sfa` reading an archive's table of contents

Affected versions of `sfa` did not bound the table-of-contents entry count read from an archive before reserving memory sized from it, allowing a tiny crafted archive to force a reservation of up to ~160 GiB, aborting the process when the allocation cannot be satisfied (out-of-memory denial of service, CWE-400).

## Details

In the table-of-contents reader (`src/toc/reader.rs`, lines 69-77 in `1.0.0`), the entry count is read as a `u32` straight from the file and passed to `Vec::with_capacity` **before** any entry is read:

```rust
let len = reader.read_u32::<LE>()?;                 // line 69: entry count, straight from the file
let mut entries = Vec::with_capacity(len as usize); // line 71: unbounded reservation, sized from the file
for _ in 0..len {                                   // lines 73-75: read entries
    entries.push(TocEntry::read_from_file(&mut reader)?);
}
reader.checksum().check(toc_checksum)?;             // line 77: checksum only verified AFTER the reservation
```

Each `TocEntry` is roughly 40 bytes, so this reserves about `len * 40` bytes (up to `u32::MAX * 40`, about 160 GiB) with no check that `len` fits within the bytes actually remaining in the file. Because the table-of-contents checksum is verified only after the reservation, it provides no protection.

The sink is reachable through the public API `sfa::Reader::new(path)` and `sfa::Reader::from_reader(reader)`. Every published version from `0.0.1` through `1.0.0` is affected, and no fixed release is available at the time of writing.

## Reproduction

A 46-byte file is enough: a ToC header (`TOC!` + a large u32 entry count) followed by the 38-byte trailer (`SFA!`, version `0x01`, checksum type `0x00`, any checksum, `toc_pos = 0`). On `1.0.0`, a count of `10_000_000` made `sfa::Reader::new` reserve 400,000,000 bytes (~381 MiB) before failing with `UnexpectedEof`.
