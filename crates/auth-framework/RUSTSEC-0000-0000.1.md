# A SAML subject token in a token exchange is accepted unsigned (0.4.x, 0.5.0-rc1) or if signed by any key it carries (0.5.0-rc18 on)

A client policy that lists `Saml2` or `Saml1` in `allowed_subject_token_types` (the default policy does not). First affected **0.4.0** (the first
release with `server/token_exchange/core.rs`).

* **0.4.0 through 0.4.40 and 0.5.0-rc1**: no feature needed. `validate_saml_token` only checked that the text contained SAML namespace markers, took
  the subject from the first `<saml:NameID>` and issued an access token. Demonstrated on unfixed 0.4.40: an unsigned two-element "assertion" for
  `admin@example` was exchanged for an access token (`scope: saml_authenticated`). `TokenExchangeService::validate_token` also reported any SAML
  token as `is_valid: true`.
* **0.5.0-rc18 through 0.5.0-rc60 and 0.6.0-rc41 through 0.6.0-rc121** (feature `saml`): `validate_saml_assertion_xml` read the verification certificate out of the subject token itself (`KeyInfo/X509Data/X509Certificate`) and checked the
signature with it: no trust anchor, no issuer-to-certificate pinning. Anyone could sign an assertion for any subject with a key pair of their own,
embed their certificate, and exchange it. The check on the signature also rebuilt `SignedInfo` by hand and never compared a `Reference` digest, so a
valid `SignedInfo` could be attached to other content (the same signed text also did not read as well-formed XML, which is why genuine IdP signatures
never verified through this validator, only forged ones built to match it).

Demonstrated on unfixed main: an assertion for `admin@victim.example`, signed with a throwaway key and carrying that key's certificate, validated.

Patched: 0.5.x and 0.6.x: `TokenExchangeManager::with_trusted_saml_issuer(issuer, certificate)` is required; with none configured every SAML subject
token is refused; the signature is verified under the configured certificate for the issuer with every reference digest recomputed, and only the
signed assertion is read. 0.4.41 has no XML signature verifier, so it refuses SAML subject tokens outright (and `validate_token` reports them invalid).
