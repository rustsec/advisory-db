# Derived Debug on configuration, request and response types printed secrets (passwords, client secrets, API keys, tokens, sessions, connection strings, MFA material) into logs

**Status (2026-10-21): no published version fixes the whole class yet; 0.6.0-rc109 fixes most of it.** An earlier version of this advisory named 0.6.0-rc97, then rc101, then rc109 as the fixing version. Each was wrong for types found later. After rc109 an audit of the audit found that its scanner did not check enum struct variants written on one line: `AuditStorage::External.api_key`, `AuditStorage::Database.connection_string` and `DeviceAuthState::Authorized.access_token` still print in rc109 and rc110. A patched version will be named here only after it is published and the scanner has been fixed to cover every shape of `Debug`-deriving field.

Many configuration, request and response types in `auth-framework` derive `Debug`, and the derived output prints their secret fields. Any `{:?}`, `dbg!`, `tracing` field or panic message that formats such a value writes the credential in clear text to logs and other diagnostic output (CWE-532).

Types and fields, by the first published version in which each was observed: 0.1.1: `Credential::Password { password }` and `Credential::Certificate { private_key, passphrase }`, `SecurityConfig.secret_key`. 0.4.0: `AuthConfig.secret`, `ClientConfig.client_secret`, `TokenRequest.client_secret` and `.password`, `ClientRegistrationResponse.client_secret`, `IntrospectionClientCredentials.client_secret`, `SamlConfig.private_key`. 0.4.1: `LoginRequest.password`, `CreateUserRequest.password`, `ChangePasswordRequest.new_password`, `DatabaseConfig.password`. 0.5.0-rc1: `RegisterRequest.password`. 0.5.0-rc18: `CreateApiKeyResponse.api_key`, `LdapConfig.bind_password`, `OpaConfig.auth_token`, `ScimClientConfig.bearer_token`.

Fix status by group (verified by reading the published crates):

* Group A, the original set of configuration and request types: redacted in 0.6.0-rc97.
* Group B, token- and device-code-carrying request and response types (for example `TokenResponse.access_token`): redacted in 0.6.0-rc101 (the change was developed as rc99).
* Group C, MFA enrolment material, backup and recovery codes and environment secrets (for example `MfaSetupResponse.qr_code`, whose otpauth URI embeds the TOTP secret): redacted in 0.6.0-rc101.
* Group D, four further types found by an external review: `UsernamePassword.value`, `EnhancedAuthorizationCode.code`, `RefreshToken.token_id` and `UserCredentials.password_hash`: redacted in 0.6.0-rc106.
* Group E, secrets held in the `Zeroizing` wrapper (17 types, plus two hand-written implementations that print such a field): `zeroize` before 1.9.1 prints the wrapped value through `Debug`, and the crate allowed `zeroize >= 1.8.2`. The manifest requires `zeroize >= 1.9.1` from 0.6.0-rc107 (0.4.34, 0.5.0-rc53 on the older lines); a consumer that resolves an older `zeroize` was exposed before that.
* Group F, an audit of the `Debug`-deriving structs with a string or bytes field (one-line enum variants were not covered, see Status) (about 94 further types: connection strings and URLs, webhook URLs and headers, about 29 kinds of session id, OIDC/CIBA/JARM/GNAP/UMA/CAS tokens and tickets, SAML responses, Kerberos tokens and key data, macaroon signatures, MFA codes, unified-storage keys): redacted in 0.6.0-rc109 for the types it covered, together with a CI audit (`tests/debug_field_review.txt`) that fails on any `Debug`-deriving type whose fields have not been reviewed.

Affected: 0.1.1 (the earliest version on crates.io) through 0.6.0-rc110. Many of these versions are yanked (all 0.6.0-rc versions before rc85 and most 0.5.0-rc versions); yanked versions are listed as affected, because yanking does not remove them from existing lockfiles. No patched release exists yet; the 0.4.x and 0.5.x lines have the same exposure. Upgrade to 0.6.0-rc109 or later now for most types, and to the release that names itself as the fix for the enum-variant types when it is published.

Impact: credentials written to logs, crash reports and other diagnostics whenever a caller Debug-formats an affected value. The defect cannot be triggered remotely by itself; it requires application code (or a tracing/logging layer) to format the value. Exposure then extends to whoever can read those logs.

Workaround before upgrading: do not Debug-format these configuration, request and response types (`{:?}`, `{:#?}`, `dbg!`, `tracing` fields, `#[instrument]` without `skip`, `unwrap`/`expect` on results that embed them); log selected non-secret fields, or wrap the value in a redacting wrapper type with a hand-written `Debug`.
