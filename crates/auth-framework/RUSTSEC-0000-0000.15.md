# Race in user registration lets concurrent sign-ups claim the same username or email

Both self-registration paths decided whether a username or e-mail address was taken by reading storage and wrote the new account afterwards. Simultaneous registrations of the same username (or address) all passed the check and all wrote.

The paths are `UserManager::register_user` (used by `AuthFramework::register_user`) and the HTTP handler `POST /auth/register` (feature `api-server`). Measured on the unpatched in-memory backend: 8 concurrent `register_user` calls for one username succeeded 8 times.

Impact: two accounts end up sharing a username or e-mail address; the username-to-user-id mapping and credentials record are last-writer-wins, so the party whose write lands last owns the name for login. No privilege escalation and no read of another account's data was demonstrated; the window is narrow.

Affected: 0.5.0-rc18 up to 0.6.0-rc45, including the latest 0.5.x release. 0.4.x and earlier have no `register_user` and no public `/auth/register`. Fixed in 0.6.0-rc46; there is no patched release on 0.5.x. Custom `AuthStorage` implementations must override `store_kv_if_absent` atomically. Workaround: serialise registrations in front of the library and rate-limit `/auth/register`.
