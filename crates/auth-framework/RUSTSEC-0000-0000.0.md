# `POST /saml/acs` logs in whoever the first assertion in the document names, not whoever the signature covers

Features `saml` and `api-server`, SAML SSO configured (`saml_sp:config`, `saml_idp:{entity}` with `signing_cert`).

* **0.5.0-rc1** (yanked): the endpoint verified no signature at all ("Basic SAML response validation").
* **0.5.0-rc18 through 0.5.0-rc60 and 0.6.0-rc41 through 0.6.0-rc121**: the signature was verified with `bergshamra` in strict mode, and then the
  user name, conditions and attributes were read from the *first* `Assertion` in the whole text. A signature proves one element genuine; it does not
  make the first assertion that one. An attacker with any genuine IdP-signed assertion (their own) adds an unsigned assertion naming another user in
  front of it; the signature still verifies, and the endpoint issues a token for the user the forged assertion names.
* Second defect: `InResponseTo` was read from the `Response` wrapper, which is not covered when only the assertion is signed. A genuine assertion
  that answered someone else's request was accepted against an attacker's own pending request.

Demonstrated on unfixed main: the endpoint returned `user_id: admin@idp` for a document holding a genuine signed assertion for `alice@idp` and an
unsigned one for `admin@idp` placed first; and accepted a signed assertion answering request `victim` under a wrapper claiming `attacker_req`.

Patched: the verified assertion (found by its unique `ID`) is the only thing read; `InResponseTo` comes from the signed assertion unless the
`Response` is signed. The IdP must have a usable pinned `signing_cert`, or SSO is not started for it.
