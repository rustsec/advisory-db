# JARM, JWT introspection and the default SAML method used fixed, published keys

Three components signed or verified with a fixed, publicly readable constant when the application had not configured its own key, so anyone who knows the constant (it is in the published source) can produce values the library accepts.

1. **JARM (JWT-secured authorization response mode).** The JARM manager signed and validated authorization-response JWTs with the fixed key `test_key_for_development_only_123456`. In 0.4.x and 0.5.0-rc1 the constant was used unconditionally; in later 0.5.0 and in 0.6.0 releases it was the fallback when no signing keys were configured and also when configured keys failed to parse. An attacker could mint an authorization-response JWT that the validator accepts.
2. **JWT token introspection.** The introspection manager verified introspection responses with the fixed key `introspection_jwt_secret_key_change_in_production`. An attacker could forge an "active" introspection response and make an arbitrary token appear active.
3. **SAML default method.** `SamlAuthMethod::default()` (feature `saml`) signed and verified tokens with the fixed secret `default-saml-secret`. A token signed with that public constant was accepted.

All three were present in the first published release of each line (0.4.0, 0.5.0-rc1, 0.6.0-rc41) and in every published version the maintainers checked after that. The fixed versions (0.4.29, 0.5.0-rc51, 0.6.0-rc85) contain none of the three constants; the managers now generate a random per-instance key or refuse to operate unconfigured.

Upgrade to the newest release of your line and configure your own signing keys and secrets. Tokens or responses produced under the old constants should be treated as forgeable: rotate secrets and invalidate outstanding tokens and sessions that depended on these components.

Versions 0.4.28, 0.5.0-rc49 and 0.6.0-rc73 fixed the earlier default-secret defect (GHSA-9r7g-3hh2-8x65) but still contained these constants; they have been yanked.
