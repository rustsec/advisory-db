# Token introspection accepts a server-issued JWT as a client assertion for client authentication

`TokenIntrospectionService` authenticated the `client_secret_jwt` and `private_key_jwt` client authentication methods by validating the supplied `client_assertion` with the server's own token manager and comparing `sub` with the claimed client id. It never checked the assertion against the client's own key or secret. Any JWT the server itself had issued with the client id as its subject and the issuer in `aud` (a `client_credentials` access token of that client, for one) authenticated as that client.

Reachability: the bundled HTTP extraction (`extract_client_credentials`) only builds `client_secret_basic` and `client_secret_post` credentials, and nothing else in the crate constructs `IntrospectionClientCredentials`. The vulnerable arm is therefore reachable only by an integrator that calls `TokenIntrospectionService::introspect_token` itself with JWT-method credentials. Deployments that use the shipped endpoint are not exposed.

Impact: a holder of such a token (one the server issued, not a forged one) can use it as the client's credential at an integrator-built introspection endpoint and read token state (active, scope, subject, client id, expiry) for arbitrary tokens. It is an information-disclosure oracle, not a way to mint or alter tokens.

Affected: 0.4.0 to 0.4.6, 0.5.0-rc1 to 0.5.0-rc27, 0.6.0-rc41 to 0.6.0-rc45 (read from the code at each published version; 0.5.0-rc1 is an assumption). Fixed in 0.4.7, 0.5.0-rc31 and 0.6.0-rc46. Workaround: never pass `ClientSecretJwt` / `PrivateKeyJwt` credentials to `introspect_token`.
