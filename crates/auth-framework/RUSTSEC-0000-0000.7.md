# Unauthenticated WebAuthn registration allows account takeover (0.5.0-rc18 to 0.5.0-rc26)

The WebAuthn (passkey) registration and sign-in endpoints of the built-in API server (feature `api-server`; the routes are mounted by `ApiServer`) did not require authentication, and bearer-token validation accepted a validly signed token whose subject had no user record. An unauthenticated attacker who could reach the API could register a credential of their own for a chosen username, sign in with it, and receive a token accepted by bearer-protected endpoints. Deployments where account ids are predictable (for example ids equal to usernames) were directly exposed to account takeover.

Affected: 0.5.0-rc18 through 0.5.0-rc26. 0.4.x is not affected (no WebAuthn HTTP endpoints). Fixed in 0.5.0-rc27 and 0.6.0-rc41. The affected releases 0.5.0-rc18 to 0.5.0-rc26 have been yanked.

After upgrading, users must re-register passkeys (all passkeys registered before the fix are ignored and some may have been planted); review sign-in logs, revoke sessions and tokens issued through the WebAuthn path, and treat any passkey whose owner you did not see register it as hostile. Workaround: do not mount the WebAuthn routes, or put authentication in front of them.
