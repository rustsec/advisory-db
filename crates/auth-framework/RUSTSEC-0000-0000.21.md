# `X509CertificateManager` could deadlock between revoking and checking a certificate

`X509CertificateManager::revoke_certificate` held the certificate store write lock while waiting for the revocation list write lock, and `check_certificate_status` held a revocation list read lock while waiting for the certificate store read lock. When a revocation and a status check ran at the same time, each waited for the lock the other held and neither returned. Every later call that needed either lock then waited too, so the manager stopped answering until the process restarted.

Only applications that expose both calls to concurrent callers are affected; the crate does not route network input to this type itself. Nothing is disclosed or altered: the effect is a hang.

Later releases (0.5.0-rc31 and newer, 0.6.0-rc45 and newer) already release each lock before taking the next. 0.4.43 does the same for the 0.4 line. Upgrade to a fixed release; a process that has hung must be restarted.
