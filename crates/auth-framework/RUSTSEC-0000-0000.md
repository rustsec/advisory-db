# Email verification token returned to unauthenticated callers

The email-verification endpoints (feature `api-server`; mounted by `ApiServer`) returned the verification token in the HTTP response. `POST /auth/resend-verification` is public by design (it takes only an e-mail address) and returned a usable token for an existing, unverified account, which `POST /auth/verify-email` then accepted; the authenticated `POST /auth/verify-email/send` returned the token to its caller as well. The response for an unknown address also differed from that for an existing one, revealing whether an account existed.

Impact: the proof-of-inbox property of e-mail verification did not hold. An account's `email_verified` flag could be set without controlling the address, so relying parties that trust `email_verified` (for example through the OpenID Connect userinfo response) could be given a false attestation.

Affected: 0.5.0-rc18 up to 0.6.0-rc45, including the latest 0.5.x release (the module does not exist in 0.4.x and earlier). Fixed in 0.6.0-rc46; there is no patched release on 0.5.x. After upgrading, install an `EmailVerificationSender`; without one e-mail verification cannot complete. Treat `email_verified` values set before the upgrade as unproven. Workaround: block `/auth/resend-verification` and `/auth/verify-email/send` at the reverse proxy, or stop trusting `email_verified`.
