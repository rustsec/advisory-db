# request_uri of a pushed authorization request is not single use under concurrent redemption

`PARManager::consume_request` (pushed authorization requests, RFC 9126) is meant to hand out a stored request exactly once. It read the request and then deleted it as two separate storage calls, so simultaneous redemptions of the same `request_uri` all succeeded (measured on the unpatched in-memory backend: 8 concurrent redemptions, up to 5 succeeded in one round).

A party that obtains a `request_uri` can redeem it at the same moment as the legitimate client and receive the same stored authorization request parameters, so the authorization server processes them twice. The PKCE code challenge stays bound to the legitimate client, so this does not by itself yield a token; the realistic effect is a replayed authorization request. It needs possession of the `request_uri` and winning a race.

Affected: every published version from 0.4.0 (the module does not exist in 0.1.1, 0.2.0 and 0.3.0) up to 0.6.0-rc45, including the latest releases of the 0.4.x and 0.5.x lines. The only patched version is 0.6.0-rc46; there is no patched release on 0.4.x or 0.5.x. Custom `AuthStorage` implementations must override `store_kv_if_absent` atomically, because the fix relies on it. Workarounds: keep PAR lifetimes short and require PKCE (`S256`).
