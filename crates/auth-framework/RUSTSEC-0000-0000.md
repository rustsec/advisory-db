# OAuth2 scope model: requested scopes not checked against the client; refresh endpoint matches scope by substring

Two components.

1. **Scope handling (feature `api-server`).** `/oauth/authorize` stored whatever scope the client asked for without comparing it with the scopes the client was registered for, and the token endpoint minted tokens from it. A token issued to an OAuth client behaved as the user's full session on the first-party API, so a client registered for a narrow scope held a token the first-party endpoints accepted as the user. Affects 0.5.0-rc18 up to 0.6.0-rc45 (no `api/oauth2.rs` in 0.4.x and earlier).
2. **Refresh by substring.** `POST /auth/refresh` decided that a token was a refresh token with `claims.scope.contains("refresh")`, so any token whose scope merely contained that text could be exchanged for a new access token carrying the user's stored permissions. Affects 0.4.1 to 0.4.6 and 0.5.0-rc1 up to 0.6.0-rc45.

Fixed: 0.4.7 (refresh substring only) and 0.6.0-rc46 (both). There is no patched release on 0.5.x. Behaviour changes on upgrade: OAuth-issued tokens no longer work on session endpoints, clients get only the scopes they are registered for, and users sign in again once. Workaround: do not register untrusted OAuth clients and do not give users roles whose names contain `refresh`.
