# Passkey authentication accepts an assertion without verifying it

First affected: **0.4.0** (first release with `complete_authentication`; 0.3.0 has none; the `passkeys` feature exists in 0.4.0 and is not
a default feature in any version). Published affected versions: 0.4.0-0.4.7, 0.4.22, 0.4.24, 0.4.25, 0.4.28-0.4.30, 0.4.33, 0.4.34
(0.4.35-0.4.39 were never published) and **0.5.0-rc1**. All are already yanked.

`PasskeyAuthMethod::complete_authentication` found the registered passkey by the credential id in the assertion and issued a token. It did
not check the challenge, origin, RP-id hash, signature or sign count (the code says "basic validation"). An application that passes a
client-supplied `AuthenticatedPublicKeyCredential` to it authenticates anyone who knows a registered credential id (not secret in WebAuthn)
as that credential's user. `authenticate` (trait path) rejected genuine assertions and did not accept forged ones.

## Patched
0.4.40 (published), 0.5.0-rc60 (published), 0.6.0-rc121 (published): the challenge from `initiate_authentication` is spent, and origin, RP-id
hash, signature against the stored public key, and sign count are verified. Credentials registered by affected versions carry no usable public
key: those users must register again.
