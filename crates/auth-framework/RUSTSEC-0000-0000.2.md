# `WsFederationClient::process_sign_in_response` accepts a hand-written token

The module is compiled in every build (no feature needed). First affected **0.5.0-rc18**. The response was parsed with string searches; the assertion
signature was never verified, `trusted_issuers` was compared with the issuer the token itself states (and an empty list accepted any issuer), and
`trusted_cert_thumbprints` was never consulted. The `wctx` check is the only gate, and the attacker's own session supplies a valid `wctx`. JWT
sign-in tokens were read the same way (the code notes that their signature is not verified).

Demonstrated on unfixed main (default features): a hand-written, unsigned assertion for `admin@victim.example` was returned as an accepted token.
Also: a token without `NotOnOrAfter` made the expiry check overflow (a panic in debug builds, a wrap in release).

Patched: a token is accepted only when its signature verifies under `trusted_signing_certificates` (for its issuer) or under a carried certificate
whose SHA-256 thumbprint is in `trusted_cert_thumbprints`; `WsFederationClient::new` fails with neither configured; JWT tokens and builds without
the `saml` feature accept nothing.
