# Placeholder OAuth2 handlers in api::oauth accepted any token, code and client

The OAuth2 HTTP handlers in `auth_framework::api::oauth` were placeholders that answered success for any input, with no verification of tokens, clients, codes or redirect URIs.

- `introspect_token` returned `active: true` with fixed claims for any non-empty token, so a resource server that trusted the endpoint accepted any token.
- `token` returned HTTP 200 and an `access_token` for the `authorization_code`, `refresh_token` and `client_credentials` grants, including with a wrong client secret.
- `authorize` redirected (HTTP 303) to any `redirect_uri` with a made-up code.
- `revoke_token` returned success without revoking anything.
- `get_client_info` returned invented client data.

Who is exposed: the handlers are `pub async fn` in `pub mod oauth` (feature `api-server`, which the default `enhanced-rbac` feature enables, so a default build compiles them). They are not re-exported at `api::` or the crate root. In 0.4.x the bundled `ApiServer::build_router` panics at startup (an axum 0.8 route syntax error), so these handlers were reachable only by an application mounting `api::oauth::*` itself. In 0.5.0-rc1 (yanked) the router built and mounted `/api/v1/oauth/{authorize,token,revoke,clients/{id}}` live, so every deployment of that release exposed the placeholders on its default router; its introspection endpoint was the real implementation, not the placeholder.

Affected: 0.4.1 to 0.4.29 and 0.5.0-rc1. 0.4.0 has no `src/api`. 0.5.0-rc18 and later and all published 0.6.0 pre-releases do not contain `src/api/oauth.rs`. Fixed in 0.4.30: all five handlers answer HTTP 501 Not Implemented. There is no patched 0.5.0-rc1 (yanked); use 0.5.0-rc51 or later, or 0.4.30. The working OAuth2 server is `auth_framework::server::oauth` and the `api::oauth2` handlers of later releases.

Workaround: do not mount `api::oauth::*`; upgrade to 0.4.30 or later of your line.
