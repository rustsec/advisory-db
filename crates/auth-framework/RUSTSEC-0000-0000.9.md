# private_key_jwt client authentication builds its verification key from public key material

`PrivateKeyJwtManager::authenticate_client` verified a client assertion with an HMAC secret built from the members of the client's public JWK instead of with the registered public key. Where an HMAC algorithm was allowed for the client, anyone who could read the client's public key could compute that secret and sign an assertion that verified. Deployments that allow only RS256/ES256 for their clients were not shown to be forgeable through this path.

Impact: authentication as any `private_key_jwt` client whose public key is known, that is, impersonating that client at the token endpoint and wherever `authenticate_client` or `FapiManager::authenticate_client_jwt` is used.

Affected: 0.4.0 to 0.4.6, 0.5.0-rc1 to 0.5.0-rc27, 0.6.0-rc41 and 0.6.0-rc42 (read from the code at each published version; 0.5.0-rc1 is an assumption). Fixed in 0.4.7, 0.5.0-rc31 and 0.6.0-rc46 (the advisory text also names the yanked 0.6.0-rc45 as fixed).

Upgrading changes behaviour: `register_client` refuses symmetric (`HS*`) algorithms and keys carrying private or symmetric parameters, and `expected_audiences` is required on 0.5.x and 0.6.x. Workaround: do not register `private_key_jwt` clients with HMAC algorithms.
