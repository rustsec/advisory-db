# Tenant isolation bypass: `PathSegmentTenantResolver` trusts a client-supplied `path` header

`PathSegmentTenantResolver` is meant to derive the tenant from the request URL
(for example `/tenants/{tenant}/...`). It read an internal `:path` entry and,
when that was absent, fell back to an ordinary request header named `path`.
Only the WebSocket dispatcher set `:path`, so on the HTTP+JSON, JSON-RPC and
gRPC dispatchers and the Axum adapter (`A2aRouter`) the tenant was taken from a
header (or gRPC metadata entry) the client controls.

A client could therefore send `path: /tenants/<other-tenant>/x` and have its
request executed as that tenant: read, list, subscribe to, cancel and create
its tasks, and read or create push-notification configurations on them. This
defeats access control enforced on the URL, such as a gateway that admits a
caller only to `/tenants/acme/*`. On JSON-RPC the header overrode the tenant in
the URL; on HTTP+JSON it was accepted on routes without a tenant prefix.

Only servers that configure `PathSegmentTenantResolver` are affected. From
0.7.0 the request handler invokes the configured resolver on every message,
task and push-configuration request; in
0.3.0 through 0.6.x the fallback existed but was reachable only if application
code called `RequestHandler::tenant_resolver()` itself. `a2a-protocol-sdk`
depends on this crate and is covered by upgrading it.

The flaw was corrected in 0.14.1 (commit `5f0bbd0`): the JSON-RPC and HTTP+JSON
dispatchers set `:path` from the request URI and the resolver reads nothing
else. On gRPC and `A2aRouter`, which carry no URL, the resolver now resolves no
tenant; deployments that used it there should switch to
`BearerTokenTenantResolver` or `HeaderTenantResolver` and set
`require_resolved_tenant(true)`.
