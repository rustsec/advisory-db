# Writes to the memory map went through a pointer derived from a shared reference

Affected versions wrote to the memory-mapped database file through a raw pointer obtained from `map.as_ptr()`, where `map` is a `&memmap2::MmapMut`. `MmapMut` has no inherent `as_ptr`, so that call resolves through `Deref` to `<[u8]>::as_ptr(&**map)`, and `MmapMut::deref` builds the slice with `slice::from_raw_parts`. The resulting pointer therefore carries shared, read-only provenance, and writing through it is undefined behaviour under both of Miri's aliasing models (Stacked Borrows reports `only grants SharedReadOnly permission`, Tree Borrows reports a child write through a `Frozen` tag).

The affected code paths were `File::write_at` and the two log-apply paths in `index.rs` and `ref_count.rs`. They are safe methods reached from the safe public API, so safe code could cause undefined behaviour.

The comments at each site reasoned about data races between threads, which is a separate concern; this issue is about the provenance of the pointer itself and is present even in a single-threaded program.

The flaw was corrected in 0.5.7 by routing all memory-map access through a `memmap2::MmapRaw` wrapper, whose `as_mut_ptr` legitimately yields a writable pointer from a shared reference.

There is no evidence of miscompilation; current rustc keeps the writes.
