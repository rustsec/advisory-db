# Transaction readers accept trailing bytes; BEEF verdicts answer valid for a raw entry that is not a transaction

Two flaws in `bsv-rs`, present in every published version before 0.8.5 and in
0.9.0-beta.1 through 0.9.0-beta.7.

The CVSS vector scores the reasonable worst case for a library: a network
service that passes a peer's bytes to the functions named below and relies on
`id()` or on the verdict. An application that passes them only bytes it
produced or has already checked is not affected.

## Trailing bytes at the transaction readers

`Transaction::from_binary` and `Transaction::from_hex` read one transaction
from the front of their input, did not check that the input ended there, and
kept the whole input as the transaction's cached serialization: `to_binary`,
`to_hex` and `id()` then answered for bytes that are not the transaction's.
`Transaction::from_json`, given a `hex` field, reads it through `from_hex` and
answers the same. `from_ef`, `from_hex_ef` and `parse_script_offsets` also
read a prefix; `parse_script_offsets` also answers for a transaction cut
inside its lock time. An application that takes bytes or hex from outside,
parses them with these readers and then uses `id()` or the serialization could
be given one transaction under another identity: the same parsed fields, a
different id.

## A raw BEEF entry that is not a transaction answered valid

`Beef::merge_raw_tx` and `BeefTx::from_raw_tx` accept raw bytes without a
`Result`. For bytes that are not exactly one transaction (a transaction
followed by bytes, a cut transaction, bytes that are no transaction at all),
`Beef::sort_txs`, `verify_structure`, `verify_valid` and `is_valid` could
answer valid, even with no BUMP and no parent in the BEEF, and, where the entry
carried a BUMP index, treat the hash of those bytes as a proven transaction id;
an entry that names it as a parent was answered valid too. For such an entry
built from a transaction followed by bytes, `Beef::find_atomic_transaction`
and `find_transaction_for_signing` hand back a transaction whose `id()` and
`to_binary()` are those of the whole bytes.

The wire readers (`Beef::from_binary`, `verify_stream`,
`Transaction::from_beef`, `from_atomic_beef`) parse every entry and are not
affected: a BEEF this crate writes from such an entry is refused by each of
them. Reaching this needs an application that passes bytes it did not parse to
`merge_raw_tx` or `BeefTx::from_raw_tx` (or carries such an entry into another
BEEF with `merge_beef`) and then relies on the verdict or on the transaction
the BEEF hands back.

## Patches

0.8.5: the transaction readers refuse a byte after the transaction
(`Serialized transaction contains trailing data`; `from_ef` and `from_hex_ef`
answer `Serialized EF transaction contains trailing data`).
`Transaction::from_reader` is the public door for reading from the front of a
longer buffer. A raw BEEF entry whose bytes are not exactly one transaction is
refused by all four verdict doors, with or without a BUMP index, and every
entry that names it as a parent is refused with it. One public function is
added (`Transaction::from_reader`); no other public item or signature changes.

`Beef::to_binary` and `to_hex` (which return no `Result` on this line) and
`to_binary_atomic` (which returns `Ok`) still write such an entry's bytes as
given; no verdict door calls that BEEF valid, and a strict reader refuses it.

No 0.9.0 prerelease published so far carries the fix: 0.9.0-beta.1 through
0.9.0-beta.7 are affected. The fix is on the `beta` branch, unreleased, and
ships in the next prerelease.

## Workarounds

Upgrade to 0.8.5. Where that is not possible, before using `id()` or the
serialization of a transaction parsed from bytes you did not produce, and
before `merge_raw_tx` or `BeefTx::from_raw_tx` of such bytes: parse them with
`Transaction::from_binary`, call `tx.invalidate_caches()` (public from 0.3.16),
require `tx.to_binary() == bytes`, and compare `tx.id()` with the transaction
id you expected. The call matters: an affected version keeps the reader's
whole input as the cached serialization, so a comparison made before it always
passes, and so does a comparison of `tx.to_binary().len()` with the input's
length. On 0.2.0 through 0.3.15, where `invalidate_caches` is not public,
rebuild the transaction from its parsed fields
(`Transaction::with_params(tx.version, tx.inputs.clone(), tx.outputs.clone(), tx.lock_time)`)
and require that its `to_binary()` equals the bytes and its `id()` the id you
expected. Do not rely on `is_valid` or `verify_valid` alone for such an entry
on an affected version.
