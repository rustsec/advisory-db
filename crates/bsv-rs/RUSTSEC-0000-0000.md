# Transaction::to_beef writes a BEEF that ends with a proven ancestor or its descendant, not the transaction, when its closure rests on a missing input

`Transaction::to_beef` and `to_beef_v1` (public since 0.2.0, the crate's
first release) collected the transaction's ancestry with the transaction
last, then sorted the entries before writing. A graph holding a proven branch
beside a branch resting on a missing source got its transaction written before
the proven ancestor, and `Transaction::from_beef(&bytes, None)` — the read
that names no txid — answered the last entry: a proven ancestor of the
transaction the caller serialized, or an unproven descendant of one. The
transaction returned is real and valid, so an application can store, index,
notify or pay by a txid that is not the one it serialized.

An application that re-serializes a peer's partial graph (the
`allow_partial` door) and reads the result without naming the txid is
affected; a read that names the txid always took the transaction, and a graph
with no proven entry was never misread. The atomic door names its subject in
the header, so its own read (`from_atomic_beef`) always took it back; a
`from_beef` of its bytes that names no txid took the header into account only
from 0.3.20 on. 1,259 of 2,000 random such graphs misidentify, measured on
every version crates.io serves (0.2.0 through 0.8.7 and the 0.9.0 betas,
the yanked 0.3.21 included).

0.8.8's two doors write the collected order — each entry's sources above
it, the transaction last — instead of sorting (the 0.9 line's next prerelease carries
the same hold). Where upgrading is not possible, name the transaction when
reading a BEEF these doors wrote: `Transaction::from_beef(&bytes,
Some(&txid))` returns it on every affected version.
