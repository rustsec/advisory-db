# Panic in `ZipFile::drop` on I/O error while draining a streaming entry

`read_zipfile_from_stream` returns a `ZipFile` whose `Drop` implementation drains the remaining entry bytes so the next entry becomes readable on the shared stream. If the underlying reader returns an I/O error during that drain — a TCP reset, a closed pipe, an interrupted read — the `Drop` calls `panic!`. Because `Drop` cannot return `Result`, this error cannot be handled by the caller at the language level; and if the drop runs while another panic is already unwinding, the second panic aborts the process immediately (`SIGABRT`), bypassing `catch_unwind`.

## Impact

Any service that iterates entries of an attacker-influenced zip stream with `read_zipfile_from_stream` — HTTP body processors, mail attachment scanners, pipeline consumers — can be crashed (panic, exit 101) or hard-aborted (double panic, `SIGABRT`, uncatchable) when the transport fails while a partially consumed entry is being dropped. Affected versions are 0.4.1 through 1.2.0, including the entire 0.6.x line (0.6.6, final release of that line). Services that download the archive to disk first and open it with `ZipArchive` are not affected (seekable path — the `Drop` drain is skipped for borrowed entries). No memory-safety impact: the failure is a controlled panic (or abort), not corruption.

## Root cause

`src/read.rs` (0.6.4, lines 1009-1037):

```rust
impl<'a> Drop for ZipFile<'a> {
    fn drop(&mut self) {
        if let Cow::Owned(_) = self.data {
            let mut buffer = [0; 1 << 16];
            // Get the inner `Take` reader so all decryption, decompression and CRC calculation is skipped.
            let mut reader: std::io::Take<&mut dyn std::io::Read> = match &mut self.reader {
                ZipFileReader::NoReader => {
                    let innerreader = ::std::mem::replace(&mut self.crypto_reader, None);
                    innerreader.expect("Invalid reader state").into_inner()
                }
                reader => {
                    let innerreader = ::std::mem::replace(reader, ZipFileReader::NoReader);
                    innerreader.into_inner()
                }
            };
            loop {
                match reader.read(&mut buffer) {
                    Ok(0) => break,
                    Ok(_) => (),
                    Err(e) => panic!(
                        "Could not consume all of the output of the current ZipFile: {:?}",
                        e
                    ),
                }
            }
        }
    }
}
```

The drain unwraps the decoder stack before reading (per the in-source comment, decryption, decompression and CRC are skipped), so drain-time errors are transport errors by construction. The panic lives inside `Drop`, which cannot propagate a `Result`.

## Attack scenario

An HTTP upload endpoint feeding a streaming body reader into `read_zipfile_from_stream`: the attacker is the uploader, sends one entry header plus partial data, then resets the request body (a single aborted connection). When the partially consumed `ZipFile` is dropped, the drain hits the transport error and panics. Under a `panic = "abort"` release profile this terminates the process immediately; under the default unwind profile the daemon comes back up and the same request can be replayed indefinitely. Deterministic per attempt; no credentials required.

## Mitigation

Interpose a never-erroring `Read` adapter between the transport and `read_zipfile_from_stream`, so the `Drop` drain observes `Ok(0)` and exits cleanly:

```rust
pub struct NeverErr<R> { inner: R, pub truncated: bool }

impl<R: Read> Read for NeverErr<R> {
    fn read(&mut self, buf: &mut [u8]) -> io::Result<usize> {
        loop {
            return match self.inner.read(buf) {
                Ok(n) => Ok(n),
                Err(e) if e.kind() == ErrorKind::Interrupted => continue, // retry, do not swallow
                Err(_) => { self.truncated = true; Ok(0) } // let the Drop drain converge
            };
        }
    }
}

// after iteration — the flag is mandatory for scanning-style consumers:
// if adapter.truncated { return Err(ScanIncomplete); }
```

Without checking `truncated`, a swallowed transport error is indistinguishable from a clean end-of-archive (truncated archives would pass as complete). Alternatively, run streaming extraction inside `catch_unwind` — noting this does not survive `panic = "abort"` builds and leaves the stream position lost.

## Fix

Fixed upstream in 1.2.1 (commit d13031cc, 2024-05-06), which replaced the panicking drain loop with error-swallowing `copy(..., sink())`. The fix was not backported: the 0.6.x line lives in the archived zip-rs/zip-old repository and 1.2.1 was subsequently yanked from crates.io. Users pinned to 0.6.x or 1.0-1.2.0 should upgrade to 1.2.2 or later (all later majors are unaffected) or apply the adapter above.

## Detection

Alert on crash signatures containing "Could not consume all of the output of the current ZipFile" in services pinned to affected versions; the string is stable across the range.
