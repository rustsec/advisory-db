# Downloaded file names can escape the destination directory in `hf-hub`

Affected versions of `hf-hub` join a downloaded file name onto the destination
directory without rejecting `..`, absolute, or Windows drive/UNC components, so a
crafted name is written outside that directory (path traversal, CWE-22).

## Details

The destination is built and written with no containment check
(`src/repository/download.rs`, line 323 in `1.0.0`):

```rust
let dest_path = local_dir.join(&params.filename);   // no `..` / absolute check
// the response body is then streamed to `dest_path`
```

The same unchecked join is used for the Xet download (line 795, `src/xet.rs:581`),
the default cache path (`src/cache/storage.rs`, `snapshot_path`), and
`HFBucket::sync` (`src/buckets/sync.rs:656`). No download path validates the name,
and an absolute name replaces the destination entirely.

The name can be supplied by the server, not just the caller: `snapshot_download`
takes each path from the repository tree listing, cache mode joins the `ETag` and
`X-Repo-Commit` response headers into the path, and `HFBucket::sync` uses the bucket
object listing.

**Who can reach it.** The Hugging Face Hub rejects `..` in repository paths, so a
genuine repository cannot supply a POSIX `../` name
([huggingface_hub#4086](https://github.com/huggingface/huggingface_hub/issues/4086)).
It is reachable in two ways:

- On **Windows**, `\`, `C:..` and `\\host\share` are valid Hub file names but path
  separators locally, so a malicious repository on the real Hub escapes the
  destination for a Windows client. Hugging Face fixed this in the Python client as
  CVE-2026-15717
  ([huggingface_hub#4540](https://github.com/huggingface/huggingface_hub/pull/4540));
  the Rust code has the same unchecked join.
- On any platform, through a malicious or mirror endpoint (`HF_ENDPOINT`), or an
  application that passes an untrusted name to `download_file`.

Every version from `1.0.0-rc.0` onward is affected (`0.x` has no server-listing
download). The code is still on `main` (`1.1.0`) with no fixed release; a fix for
the download paths, but not `HFBucket::sync`, is proposed in
[#243](https://github.com/huggingface/hf-hub/pull/243).

## Reproduction

Point `HFClient::builder().endpoint(..)` at a loopback server whose tree listing
returns `{"path": "../escape.txt", ...}` and serves any bytes, then call
`client.model("o","r").snapshot_download().local_dir(dir).send().await`. On `1.0.0`,
`escape.txt` is written next to `dir` instead of inside it.
