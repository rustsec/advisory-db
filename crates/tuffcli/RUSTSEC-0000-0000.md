# Path traversal lets a capability read or write outside the project, and a lockfile make Tuff delete outside directories

Two related path traversal bugs let a capability, a capability pack, or a committed `tuff.lock` make Tuff read, write, or delete files outside the directories it manages. Both require a user to run a Tuff command on untrusted input, such as `tuff add` on a capability from someone else's repository, or `tuff delete` in a cloned repository.

## Manifest `files` entries could escape the capability directory

Each entry in a `tuff.toml` `files` list, and a tool's `entrypoint`, was joined to the capability directory to read it and to the agent directory to write it, without checking the path. An entry such as `../../outside.txt` or an absolute path read a file from outside the capability and wrote it anywhere the user can write, for example `.git/hooks/`, which leads to code execution on a later `git commit`. Listed files that were symbolic links were followed, so their targets, for example a private key, were copied into the project. Native hook sources given with `tuff add hook --hook-file` followed symbolic links the same way.

## Capability ids could aim an install or a delete outside the project

A capability id names the directory Tuff installs it into and the directory `tuff delete` removes, and was only required to be non-empty. A `tuff.lock` entry named `../../../victim` made `tuff delete` recursively remove a directory outside the project. A manifest `id`, a `--name` override, or a pack member id could aim an install the same way.

## Fix

Version 0.10.0 requires every `files` entry and entrypoint to be a relative path inside the capability directory with no `..`, no leading `/`, and no symbolic link along it, and refuses symbolic links for native hook sources. Tuff also refuses to write any file outside its install directory. Every capability id must be a relative path of plain names, and an invalid name in `tuff.lock` makes Tuff refuse the lockfile as corrupt.
