# Several soundness issues in yaxpeax-x86 (fixed in 2.2.1)

`yaxpeax-x86` 2.2.0 and earlier contain several soundness issues, all fixed in 2.2.1. In each case, triggering the undefined behavior requires a caller to use the API in an unusual way (the maintainer notes none are reachable through ordinary decode-and-inspect usage); they are recorded as soundness bugs for completeness.

1. **Invalid `ComplexOp` via `transmute` (`InstBehavior::as_complex_op`).** `as_complex_op` transmutes an `Opcode` into a `ComplexOp` (`src/long_mode/behavior.rs:514`, `src/protected_mode/behavior.rs:523`, `src/real_mode/behavior.rs:533`). The behavior table marks `Opcode::Invalid` (0x23) as `set_complex(true)`, but no `ComplexOp` variant has that value, so transmuting it constructs an invalid enum discriminant — undefined behavior. Reachable from safe code via `Instruction::default().behavior().as_complex_op()`, or after a `decode_into()` failure if the caller ignores the `Err` and the resulting `Invalid` opcode and still queries behavior. Confirmed under Miri (Stacked and Tree Borrows): "constructing invalid value of type ComplexOp: encountered 0x00000023, but expected a valid enum tag".

2. **Out-of-bounds access from externally mutated `prefixes`.** A caller that writes to the `prefixes` of a decoded instruction can cause an out-of-bounds access in broadcast formatting.

3. **Out-of-bounds access from a deserialized `RegSpec`.** A `RegSpec` deserialized via `serde` can hold a value that violates the type's invariants, causing an out-of-bounds access in `Display`.

4. **Non-UTF-8 bytes appended to a `String` via `DisplayRules`.** A custom `DisplayRules` implementation that conforms to the documented contract can append non-UTF-8 bytes to a `String`.

## Mitigation

Upgrade to `yaxpeax-x86 >= 2.2.1`, which replaces the unchecked `transmute` path, validates externally supplied data, and closes the formatting gaps.
