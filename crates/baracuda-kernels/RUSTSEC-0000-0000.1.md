# Safe GEMM plans did not bounds-check the bias vector: out-of-bounds device memory read

The FP8, INT4 and bespoke-RRR integer GEMM plans in `baracuda-kernels` (`Fp8GemmPlan`, `Int4GemmPlan`, and `IntGemmPlan` with the bespoke row-row-row layout) accept an optional bias as a `VectorRef` whose `len` field is public. For the `Bias`, `BiasRelu`, `BiasGelu` and `BiasSilu` epilogues, the safe `run()` checked only that `len` equals `N` (and in the integer plan, not even that), never that the `DeviceSlice` behind the vector actually holds `N` elements. The epilogue kernel reads `bias[0..N]`, so a bias slice shorter than `N` made the kernel read past the end of the allocation.

Not affected: the CUTLASS-backed `IntGemmPlan` (RCR layout) and the float GEMM validator. This is a separate defect from the strided-view bounds issue in the same crate (RUSTSEC advisory for GHSA-973r-348p-pphq, fixed in 0.0.1-alpha.137): alpha.137 added bounds checks for the matrix views but not for the bias vector.

Affected: every published version, 0.0.1-alpha.26 (the first published) through 0.0.1-alpha.137. The code was introduced on 2026-05-13 (commit c471106d, before the first published version) and the three plans and the length-only check are present in the published alpha.26 package. Fixed in 0.0.1-alpha.138: the plans check the bias slice against `N` and return `Error::BufferTooSmall` / `InvalidProblem`. This is a behaviour change: launches with an undersized bias slice that previously ran now fail.

Impact: out-of-bounds read of GPU device memory (information disclosure of adjacent allocations in the same process, or corrupted epilogue results) from safe Rust, whenever the bias length can be influenced by untrusted input (for example a model file) or is computed wrongly. Only device memory read by the kernel is involved; no write and no host memory access was identified. Action: upgrade to 0.0.1-alpha.138 or later. Workaround before upgrading: ensure every bias `DeviceSlice` holds at least `N` elements.
