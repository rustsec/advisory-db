# Safe `run()` did not bounds-check strided tensor views: out-of-bounds device memory read and write

The plans in `baracuda-kernels` (`UnaryPlan`, the GEMM, reduction, attention and other plans) accept `TensorRef` / `TensorMut` / `MatrixRef` views whose `shape` and `stride` fields are public. The safe `run()` of each plan checked only that the `DeviceSlice` behind a view held at least `numel` elements, not that the largest element offset reachable through `shape` and `stride` lies inside the slice. A view such as `shape = [N]`, `stride = [2]` over an `N`-element slice therefore made the kernel read (inputs) or write (outputs) up to N-1 elements past the end of the allocation. The same applies to other strides, to `ContiguizePlan` source offsets, and to the integer/FP8/INT4/binary GEMM plans that had no buffer check at all.

Affected: every published version, 0.0.1-alpha.26 (the first published) through 0.0.1-alpha.126. Fixed in 0.0.1-alpha.137 (alpha.127 to alpha.136 were never published): every plan now checks the reach of every view against its slice and returns `Error::BufferTooSmall` / `InvalidProblem`. This is a behaviour change: launches that previously ran with an over-reaching view now fail.

Impact: out-of-bounds reads of GPU memory (information disclosure of adjacent allocations in the same process) and out-of-bounds writes to it (corruption of other tensors or driver allocations), from safe Rust, whenever shapes or strides can be influenced by untrusted input (for example a model file) or are computed wrongly. The maintainers report a reproduction on an RTX 4070 in which 32 of 64 elements were clobbered or leaked. Only device memory accessed by the kernels is involved; no host memory access was identified. Action: upgrade to 0.0.1-alpha.137 or later. Workaround before upgrading: validate every view's reach against its buffer before constructing the arguments.
