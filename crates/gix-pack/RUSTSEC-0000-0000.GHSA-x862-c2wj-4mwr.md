# Pack object counts can trigger infallible allocation failure

gix-pack preallocates its delta-resolution tree from the object count advertised in a pack header. The initial vectors use infallible exact reservations before object bodies are processed, and the allocation limit used during delta resolution does not protect these reservations.

A malicious Git server can advertise an excessive object count during clone or fetch. If the allocator rejects the reservation, the process can abort instead of returning a pack-processing error. Whether a short pack header alone triggers allocation failure depends on the allocator and operating system's memory-overcommit behavior; a fixed memory size or an unconditional abort on every system is not established.

Update to gix-pack 0.75.0 or later. The fix makes initial tree reservations fallible, checks capacity arithmetic, and applies the existing per-allocation limit to the initial vectors.

Reported by zx (Jace), GitHub user `manus-use`.
