# Incorrect results from erf, erfc, normal_cdf, hypergeom_2f1, betainc and other special functions

Versions 1.0.0 through 1.0.4 of `zenith-float-num` return incorrect values
from several special functions for some inputs. No error is returned, so the
wrong values can propagate silently into downstream calculations. The
functions are re-exported by the `zenith-float` crate, so every user of
`zenith-float` 1.0.0 through 1.0.4 is affected.

This is a correctness problem, not a memory-safety problem. It is filed as an
informational notice so that users who depend on these functions learn that
they should upgrade.

## Affected functions

- `erf` and `erfc` return wildly wrong values for |x| >= 4 at every
  precision, and `normal_cdf`, which is computed from them, is wrong in the
  same range of its standardized argument. At 256 bits of precision:

  | Call | Returned | Correct value |
  | --- | --- | --- |
  | `erfc(4.2)` | 1.98e349 | 2.855e-9 |
  | `erfc(10)` | 4.99e17 | 2.088e-45 |
  | `erfc(12.5)` | 7.69e-56 | 6.232e-70 |
  | `erf(4)` | -4.40e366 | 0.99999998458 |
  | `normal_cdf(-6)` (mean 0, sd 1) | 1.53e433 | 9.87e-10 |

  The divergent asymptotic series for `erfc` was used for every |x| >= 4 and
  summed past its smallest term.
- `hypergeom_2f1` returns incorrect values for 1/2 < z < 1 (for example
  2F1(1,1;2;0.7) returns 6.06e175 instead of 1.71996...) and NaN for z <= -1
  when b - a is an integer.
- `betainc` returns incorrect values for large parameters (for example
  I_0.7(30.5, 2.25) returns 2.68e240 instead of 3.03e-4).
- `gamma` and `digamma` are limited to about 274 and 530 correct bits at any
  precision, and `gamma`, `ln_gamma` and `digamma` lose further accuracy on
  32-bit targets. `ln_gamma(1e20)` returns infinity.
- `ei`, `fresnel_s`, `fresnel_c`, the Airy functions and the real Bessel
  functions return few or no correct bits for some arguments.
- The complex (`ExactComplex`) versions of `erf`, `erfc`, `ci`, `ei`, the
  Fresnel, Airy, Bessel and gamma functions and `hypergeom_2f1` return
  incorrect values, NaN or the wrong branch for some arguments.
- `ExactNum::cmp` returns unnormalised values, so the crate's quadrature,
  root-finding, ODE and Chebyshev routines return `None` for intervals whose
  endpoints share a binary exponent, such as `[2, 3]`.

## Fix

Version 1.0.5 of `zenith-float-num`, `zenith-float` and `zenith-float-macro`
corrects all of the above, with no public API changes. Each fixed case is
covered by a regression test against mpmath. Upgrade with
`cargo update -p zenith-float -p zenith-float-num`. The full list is in the
1.0.5 changelog.
