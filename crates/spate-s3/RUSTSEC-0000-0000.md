# A small compressed object can exhaust memory in the S3 source

The S3 source in affected versions decodes each gzip or zstd chunk in full, and queues every record the chunk produces before the pipeline drains any of them. A chunk is at most `source.s3.chunk_bytes` of compressed input (512 KiB by default), but nothing bounded the decoded bytes or the number of records it queues.

An 8.5 KB zstd object of short NDJSON lines takes a pipeline running 0.3.0 to 2.6 GB of resident memory, and under a 1 GiB memory limit the same object gets the process killed. With the default `compression: auto`, any object whose key ends in `.gz`, `.gzip`, `.zst` or `.zstd` is decompressed, so anyone who can write an object under the source's prefix can trigger it. The object is read again each time the split holding it is retried, so it can take down each process that takes the split over, until the split is quarantined. Uncompressed objects are not affected.

The flaw was corrected in 0.4.0 (commit `d27df236`). The source now decodes a chunk in steps of about 256 KiB of output and moves each step's records into the batch before decoding the next. The zstd decoder's window is also capped at 128 MiB per lane, which is the zstd library's default, and a frame that declares more fails its unit as undecodable.
