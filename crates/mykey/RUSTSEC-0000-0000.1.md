# MIKEY message MAC is never verified on receive, so forged messages are accepted

`mykey` implements MIKEY (RFC 3830) for SRTP key exchange. In versions up to and
including 1.0.0, no receive path verified the MIKEY message authentication code.

`crypto::verify_mac` existed and was correct, but it was called only from unit
tests — neither `MikeyMessage::from_bytes` nor `MikeyMessage::complete_psk`
invoked it.

`new_psk_init` computed an HMAC-SHA-1-160 over the serialized message and
appended it, so the tag was present on the wire and looked like integrity
protection. It was decorative: a receiver accepted any message regardless of
whether the MAC was correct, wrong, or absent.

## Consequences

- An attacker able to inject or modify MIKEY messages in transit faced no
  integrity check. Modified RAND, SSRC or security-policy payloads were accepted
  silently.
- Pre-shared key mode therefore provided no mutual authentication, despite the
  documentation claiming that it did. Possession of the pre-shared key was never
  actually proven by either party.
- Replayed init messages were not rejected.

In affected versions the practical severity was bounded by GHSA-fwjg-cm92-j3hj
(cleartext TGK), which already let a passive observer recover the key material
outright without needing to forge anything.

## Affected versions

All published versions before 2.0.0 (0.1.1, 0.2.0, 0.2.1, 1.0.0). There is no
unaffected earlier release to downgrade to.

## Patched versions

Fixed in 2.0.0. `complete_psk` now verifies the message MAC before any
decryption, so a message that fails authentication yields no key material at
all. A `MacAlg::Null` payload, an absent MAC and a truncated MAC are each refused
rather than treated as "no check required".

The authentication key is now derived from the pre-shared key per RFC 3830 §4.1.4
rather than from the TGK — a prerequisite, since verifying against a TGK-derived
key would have been circular while the TGK travelled in the message itself.
2.0.0 also adds optional §6.9 verification messages, giving the exchange genuine
mutual authentication.

Note that 2.0.0 does **not** add replay protection: a captured PSK-Init can still
be replayed and will be accepted. That gap is tracked publicly at
<https://github.com/waxspin/mykey/issues/24> and is not covered by this advisory.

## Workarounds

Upgrade to 2.0.0. Failing that, treat parsed MIKEY messages as unauthenticated
input: do not rely on pre-shared key mode for peer authentication or message
integrity, and carry it over a transport that provides both.
