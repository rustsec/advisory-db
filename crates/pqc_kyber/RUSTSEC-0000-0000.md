# pqc_kyber: AVX2 backend skips Fujisaki-Okamoto implicit rejection, enabling chosen-ciphertext key recovery

## Summary

When `pqc_kyber` is built with the opt-in `avx2` feature on x86_64, its
constant-time conditional-move routine `cmov` is a no-op: it never performs the
copy. That `cmov` is exactly the step that applies the Fujisaki-Okamoto (FO)
implicit rejection during decapsulation. With it disabled, decapsulating an
*invalid* ciphertext no longer returns a key-independent pseudorandom value;
it returns a value that depends on the decrypted plaintext of the
attacker-chosen ciphertext. This restores the chosen-ciphertext decryption
oracle that the FO transform exists to remove, and yields full recovery of the
static secret key.

The attack requires no timing measurement, no side channel, and no faults; only
the ability to submit ciphertexts to a decapsulation operation under a reused
key pair and observe the resulting shared secret.

## Affected configuration

Reachable only in builds with `features = ["avx2"]` on an x86_64 target. The
default (reference) backend and all non-x86_64 targets are unaffected.

## Root cause

`src/avx2/verify.rs`:

```rust
pub fn cmov(r: &mut [u8], x: &[u8], mut len: usize, mut b: u8) {
    let bvec = _mm256_set1_epi64x(b as i64);        // BUG
    for i in 0..(len / 32) {
        let rvec = /* load r */;
        let xvec = /* load x */;
        let rvec = _mm256_blendv_epi8(rvec, xvec, bvec);
        /* store rvec into r */
    }
    // scalar tail runs only when len % 32 != 0
}
```

`_mm256_blendv_epi8(r, x, mask)` copies each byte of `x` only where the
corresponding byte of `mask` has its high bit set. For "copy when `b == 1`" the
mask must be all-`0xFF`. Broadcasting the 64-bit value `b` with
`_mm256_set1_epi64x` makes each lane `0x00000000_00000001`, so every byte's high
bit is `0` and `blendv` copies nothing. The vectorised loop is a no-op for any
`b`. The correct form (as in the pq-crystals reference AVX2 code) negates the
condition byte and broadcasts per byte:

```rust
let b = b.wrapping_neg();               // 0x00 or 0xFF
let bvec = _mm256_set1_epi8(b as i8);   // all bytes 0x00 or 0xFF
```

Note: the routine's scalar tail also negates `b`; a complete fix removes that
second negation so the tail is not double-negated. The tail is unreached for
`len == 32` (the decapsulation call), but a general fix must account for it.

## Reachability

`src/kem.rs`, `crypto_kem_dec`:

```rust
let fail = verify(ct, &cmp, KYBER_CIPHERTEXTBYTES);   // 1 on invalid ciphertext
cmov(&mut kr, &sk[END..], KYBER_SYMBYTES, fail);      // FO implicit rejection
```

`KYBER_SYMBYTES == 32`, so the copy runs entirely through the broken 32-byte
vector loop with no scalar tail. On an invalid ciphertext (`fail == 1`) the
pre-key `kr[0..32]`, which equals `G(m' ‖ h(pk))[0..32]`, is not overwritten
with the rejection secret `z`. The returned shared secret is therefore

```
ss = KDF( G(m' ‖ h(pk))[0..32]  ‖  H(ct) ),   where  m' = Decrypt(ct)
```

Every input except `m'` is public, so an attacker can compute the expected `ss`
for any guessed `m'` and compare it to the oracle output. That is a
plaintext-checking oracle.

## Impact

Complete IND-CCA break. The plaintext-checking oracle drives a standard
chosen-ciphertext key-recovery attack and extracts the entire static secret
key. Any protocol reusing a Kyber key pair across decapsulations (static or
long-term KEM keys, KEMTLS, HPKE recipients, pinned keys) is exposed;
ephemeral-only key shares are not.

## How to reproduce

No special hardware beyond an x86_64 CPU with AVX2.

1. Build the crate with the vulnerable backend: `--features avx2` and
   `RUSTFLAGS="-C target-feature=+aes,+avx2,+sse2,+sse4.1,+bmi2,+popcnt"`.
2. Probe the primitive: `cmov(len = 32, b = 1)` copies all 32 bytes on the
   reference backend and copies nothing on the avx2 backend.
3. Decapsulate a corrupted ciphertext under a fixed key pair on both backends:
   the reference backend returns a key-independent value; the avx2 backend
   returns a message-dependent value that the attacker recomputes from the
   decrypted `m'` using only public data (the plaintext-checking oracle).
4. Run the chosen-ciphertext attack using only the public key and the
   decapsulation oracle.

Observed on a self-contained PoC (ML-KEM-768): the oracle is confirmed, and the
chosen-ciphertext attack recovers the full secret key in 4,272 decapsulation
queries with 0/768 recovered-coefficient mismatches against ground truth; the
recovered key reproduces real decryption on 64/64 random ciphertexts.

## Maintenance status

The crate is unmaintained. Its last release (`0.7.1`) and its last repository
commit both date to August 2023 (roughly three years with no updates), and no
fix has shipped for previously reported security issues. There is therefore no
patched version and none is expected.

## Mitigation

- Migrate to a maintained implementation such as `ml-kem`.
- If remaining on this crate, do not enable the `avx2` feature; the default
  reference backend performs implicit rejection correctly.
- Do not reuse a Kyber key pair across decapsulations.
