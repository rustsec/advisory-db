# `fsgate-broker` on macOS accepts a `--socket` directory whose access list lets other users replace the socket

`fsgate-broker --socket` refuses a socket path through a directory that another user owns, or can write to without the sticky bit, because such a user could replace the socket and answer the next client that connects. The check read only the mode bits. On macOS, a directory's extended access list can give other users rights the mode bits do not show, so a `0700` directory with `everyone allow add_file,delete_child` was accepted, and any user could replace the socket in it.

Only `fsgate-broker --socket` on macOS is affected, and only when a directory on the socket's path has such an entry. Linux is not affected, because a POSIX access list's mask is the group bits, which the check reads. Releases before 0.4.0 did not check the socket's directories at all (GHSA-w59j-6qm2-fmxx).

The flaw was corrected in 0.5.0: on macOS, the check also reads each directory's access list and refuses an `allow` entry that gives `add_file`, `add_subdirectory`, `delete_child`, `delete`, `writesecurity`, or `chown`. `chmod -N` removes the list.
