# A symlink or another case reaches a nested grant with fewer rights using the outer grant's rights

A `Gate` accepted a grant nested inside another with fewer rights, but routes each request by name, so it could not hold that policy. With `/proj` granted read-write and `/proj/.git` read-only, a request for `/proj/link/hooks/pre-commit`, where `link` is a symlink to `.git`, routed to `/proj` and wrote into `.git` with `/proj`'s rights. On a case-insensitive filesystem, as macOS uses by default, `/proj/.GIT/...` did the same with no symlink. It worked through a `Broker` and `fsgate-broker --grant` too, so a worker that could make a symlink in `/proj` could plant a git hook. After `lock()` the kernel allowed the same, because Landlock allows what any rule allows.

Only a policy that nests a grant with fewer rights inside another grant is affected.

The flaw was corrected in 0.5.0: `Gate::grant` and `Gate::narrow` refuse such a nested grant with `GateError::NestedGrant`, reading nesting from the directories' device and inode numbers, and `fsgate-broker` refuses such `--grant` flags at startup. This is a breaking change for those policies. To keep part of a granted directory read-only, grant the parent read-only and the writable parts beneath it.
