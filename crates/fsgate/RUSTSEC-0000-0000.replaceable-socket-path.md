# `fsgate-broker`: a `--socket` path through a directory other users can write can be replaced

Workers find `fsgate-broker` by its `--socket` path, and the broker did not check the directories on that path. If one belonged to another user, or another user could write to it and it was not sticky, that user could rename the broker's socket away and bind their own. A worker that connected then talked to their broker: it read the files that broker chose and wrote to the descriptors it handed back. From 0.2.0, the `chmod` that makes the socket `0600` also followed the path, so in such a directory it could be redirected to another file of the broker's user.

Without `--socket`, `fsgate-broker` 0.2.0 and later passes its command a connection with no path, which is not affected.

The flaw was corrected in 0.4.0: before binding, `fsgate-broker` checks every directory the socket path passes through, as given and after resolving symlinks, and exits if one belongs to another user or is writable by group or others without the sticky bit. On macOS, access lists were still missed until 0.5.0 (GHSA-3gpr-5hwr-fvcv).
