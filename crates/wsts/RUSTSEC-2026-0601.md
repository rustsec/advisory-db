# FROST coordinator accepts unvalidated DKG polynomial commitments

The FROST coordinator (`state_machine::coordinator::frost::Coordinator`) did not
validate the DKG public shares it received. It stored each polynomial commitment
at receipt without checking it, and computed the aggregate public key from its
own copy without checking it either. A signer that is a member of the signing
set could therefore make the coordinator hold a commitment with no valid proof
of knowledge of its constant term, or with the wrong number of coefficients,
including none.

Two consequences, both requiring control of a signer in the set. A malformed
commitment broadcast to every participant is correctly rejected by honest
signers, but the coordinator has already stored it; if the coordinator was
restored from saved state with an existing group key and signing continues under
that key after the failed re-keying, the next signing round indexes the
malformed commitment and the coordinator process panics. A commitment delivered
only to the coordinator, on a transport that does not enforce broadcast, lets the
signer make the coordinator compute an aggregate public key that no honest
signer holds and that the signer controls. No key material is disclosed and no
signature is forged.

The FIRE coordinator (`state_machine::coordinator::fire::Coordinator`) validates
commitments and is not affected.

Version 15.0.1 validates every commitment at receipt and again before the
aggregate key is computed, matching the FIRE coordinator. Users of the FROST
coordinator should upgrade. If that is not possible, use the FIRE coordinator,
take the group key from the signers' DKG results rather than from the
coordinator, and run DKG again before signing after any failed round.

Reported by hokvo (Gleb) through GitHub private vulnerability reporting.
