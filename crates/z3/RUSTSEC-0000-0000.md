# Leaked AST handles can wrap Z3's reference count and free a live AST

Every z3 AST handle owns one native reference: creating or cloning a handle calls `Z3_inc_ref`, and dropping it calls `Z3_dec_ref`. In Z3 releases before 5.4.0 the AST reference count is a 32-bit counter that release builds increment without an upper bound. `std::mem::forget` is safe, so safe code can leak about 2^32 handles to one AST until the count wraps, and dropping another handle then frees the AST while a live handle still points to it. `Clone` is not needed for this: Z3 interns constants, so each call to `Bool::new_const("x")` returns the same AST and takes one more reference.

A `#![forbid(unsafe_code)]` driver triggers this with z3 0.22.0 and z3-sys 0.14.1 on default features, linked against Z3 5.3.3 (the official release binary, and a release build from the source tarball). Under gdb, Z3 frees the AST inside `Z3_dec_ref` when the second handle is dropped, and formatting the surviving handle then reads the freed node. Without gdb, Z3 stops at that point with an "UNEXPECTED CODE WAS REACHED" assertion. AddressSanitizer does not report it, because Z3 returns the node to its own pool allocator. With one fewer leaked handle, the AST is not freed. The z3 maintainer acknowledged the overflow in #614.

Z3 5.4.0 saturates the count instead of wrapping (commit 472ec49), and z3-sys 0.14.2 uses Z3 5.4.x with `bundled` and defaults to Z3 5.4.1 with `gh-release`. The z3 crate code involved is unchanged in 0.25.0, and by default it links the system Z3, with 4.13.3 as the oldest supported version. Builds linked against a Z3 older than 5.4.0 remain affected.
